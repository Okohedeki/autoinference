# Slotting 2,960 Inference Rows Into Maxbox

The ten source-organized note files hold **2,960 technique rows** (vLLM 271, SGLang 212, DeepSeek 138, TensorRT-LLM/FlashInfer/NVIDIA 366, llama.cpp family 257, competitions and benchmarks 141, systems venues 317, ML venues and surveys 783, compilers/DSLs/libraries 269, other engines 206), but they describe far fewer distinct things: the production engines re-implement the same ~60 mechanisms under different registry names, and the research venues add long tails of variants in four slots (speculative decoding 277 rows, KV selection 237, weight quantization 326, GEMM kernels 311). My working estimate, from the duplicate table in section 1, is that a dedup pass will yield **roughly 1,000 canonical techniques in ~150 families**, of which about 60 are implemented in three or more engines and therefore have a verified reference to test a plugin against. The hardware split is sharp and well documented: the Ada sm_89 + AVX2 toolbox is FlashAttention-2/FlashInfer FA2 paths, Marlin and llama.cpp MMQ/MMVQ dequant GEMMs, CUTLASS 2.x FP8 (examples 58/64/94), INT8 IMMA, 2:4 sparse tensor cores, cp.async pipelines with `mma.sync`, CUDA graphs, Triton/Helion/TileLang/CuTe-DSL warp-level kernels and cuTile; everything built on TMA, `wgmma`, `tcgen05`, clusters, PDL, FP4 MMA, FlashMLA, DeepGEMM, DeepEP, FA3/FA4, Machete, QuTLASS, DeepInfer, AMX or AVX-512 is porting material only. External validation is converging on one protocol (CUDA events, warmup plus 10–50 timed runs, L2 flush, locked clocks, hidden input distributions, reward-hack audits), and because the Open Kernel Challenge judge is a KernelBot derivative, a single `task.yml`/`reference.py` adapter covers GPU MODE and OKC. Every engine exposes the same six seams (attention backend, MoE runner × all-to-all, quant scheme, spec proposer, KV connector/tier, CUDA-graph/compile mode) plus kernel-selector registries, which fixes maxbox's slot contracts. The notes could not verify about 15% of rows (blog titles, memory, 404'd pages), and the richest unmined sources are the OKC per-problem shapes behind login, the FastKernels/SOL-ExecBench task lists, and ~600 research rows whose gains were never retrieved. The ingestion plan at the end turns the ten files into a catalog with a mechanism-fingerprint dedup key and a first batch of 24 plugins for the user's RTX 4090 + i7-10700K box, all of which run on the pinned llama.cpp v0.7.0 or on Ada-compatible libraries.

The duplicate structure is the main finding for ingestion. The table below lists the techniques that appear in three or more sources under different names, with row pointers; these become the seed alias table for dedup (section 6). ## The Ada sm_89 + AVX2 line splits every slot in two

The compilers researcher states the rule most compactly: the sm_89 fast path is "cp.async multi-stage pipelines + mma.sync (fp16/bf16/int8/fp8) + register dequant + swizzled smem + persistent tile loop + split-K/stream-K + fused epilogue + CUDA graphs", and "everything TMA/wgmma/cluster/CLC/tcgen05-based is a no-op or compile error on Ada" (`compilers_dsls_libraries.md`, Inferences). The sources back this with explicit gates rather than assumptions. CuTe DSL documents "Ampere and Ada: warp-level MMA; Hopper: wgmma+TMA; Blackwell: tcgen05+TMEM" ([CuTe DSL overview](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/overview.html)). Triton's persistent-matmul tutorial gates TMA on CC ≥ 9, CLC on CC ≥ 10, and warns that the TMA variants "will fail on devices with small shared memory (RTX-4090)" ([Triton 09](https://triton-lang.org/main/getting-started/tutorials/09-persistent-matmul.html)). Helion's `tensor_descriptor` indexing "requires Hopper or newer" and warp specialization "requires Blackwell or newer" ([Helion](https://github.com/pytorch/helion)). cuTile is the inverse case, the one NVIDIA tile DSL whose README states Blackwell and Ampere/Ada support today with Hopper "coming" ([cutile-python](https://github.com/NVIDIA/cutile-python)). On the library side, FlashInfer lists sm_75, 8.0, 8.6, **8.9**, 9.0, 10.0, 10.3, 11.0, 12.0, 12.1 ([FlashInfer](https://github.com/flashinfer-ai/flashinfer)); cuSPARSELt 2:4 lists sm_89 ([cuSPARSELt](https://docs.nvidia.com/cuda/cusparselt/index.html)); CUTLASS ships Ada-specific FP8 examples 58, 64 and 94 ([CUTLASS examples](https://github.com/NVIDIA/cutlass/tree/main/examples)); Transformer Engine confirms FP8 on Ada ([TE](https://github.com/NVIDIA/TransformerEngine)); Marlin needs CC ≥ 8.0 and is "not yet optimized for Hopper" ([Marlin](https://github.com/IST-DASLab/marlin)); FA2 runs on Ampere, Ada and Hopper while FA3 is H100/H800 only ([flash-attention](https://github.com/Dao-AILab/flash-attention)).

TensorRT-LLM's quantization matrix is the most precise per-format gate in the notes and transfers directly to maxbox's precondition field: FP8 per-tensor covers Ada, Hopper, Blackwell and Rubin but not Ampere; FP8 block scaling (DeepSeek 128×128) covers Hopper, datacenter Blackwell and Rubin but **not sm_120, Ada or Ampere**; FP8 rowwise is Hopper-only; W4A16 AWQ/GPTQ is Ampere+; W4A8 (INT4 weight, FP8 activation) covers Ada, Hopper, Blackwell DC and Rubin but not sm_120 or Ampere; NVFP4 and MXFP4 are Blackwell/Rubin only; FP8 KV cache is the one quantized-KV option that reaches Ampere ([TRT-LLM quantization](https://nvidia.github.io/TensorRT-LLM/features/quantization.html)). Note the contradiction maxbox must resolve by measurement: CUTLASS example 94 is an Ada FP8 blockwise GEMM, so the DeepSeek block-scaled recipe is implementable on sm_89 even though TRT-LLM and vLLM (E#87: SM90/SM100/SM120) do not ship it there.

## Benchmarks converge on one timing protocol maxbox can adopt

The competitions file's central inference is that OKC's judge "builds on GPU MODE's reference-kernels and kernelbot", confirmed by an independent audit that found OKC's seeds fit reference-kernels' Cantor pairing, that exit code 112 equals KernelBot's `VALIDATE_FAIL`, that the modes `test/benchmark/leaderboard/profile` and the `submission.py` + `generate_input/ref_kernel/check_implementation` + `problems/<p>/task.yml`+`reference.py` layout are identical, and that the `# okc: problem=` directive mirrors `#!POPCORN leaderboard` ([OKC llms.txt](https://openkernelchallenge.dev/llms.txt); [openkernelchallenge-audit](https://github.com/msaroufim/openkernelchallenge-audit)). So one adapter covers both. Its additions for OKC are the CUDA-graph capturability check, the untimed `prepare(weights)` stage (≤ 300 s; weights may be repacked or losslessly compressed but never dropped in precision), the in-run SGLang baseline, and per-load geometric-mean aggregation. The rules worth encoding as adapter assertions: no `.item()`, `.cpu()`, `synchronize()` or value-dependent allocation; activations stay BF16 where SGLang keeps them BF16; FP8 KV stays FP8; queries may round to FP8 E4M3 at coarsest; attention must cover every key; the FP32 router may be BF16 hi+lo with FP32 accumulate; final review reruns top entries on scored, held-out and nearby shapes on medians; and removal applies for timing tamper, work outside timed calls, output caching/replay or lower precision ([llms.txt](https://openkernelchallenge.dev/llms.txt)). The user's verified facts (one H200 judged against SGLang's kernels, each run as a CUDA graph, cold L2 between runs, new random inputs with per-problem tolerance, loads of 1/16/32 users including an 8-token verify step, current bests 1.45×/2.73×/2.33×/1.94×/1.74×, Andromeda as third organizer) extend what the notes could confirm: `llms.txt` confirms "one decode step or an 8-token verify block" and "aggregates load speedups", while the exact load ladder, tolerances and shapes are only exposed via `okc show <problem>` / `GET /problems/{problem}` behind a human `okc login` (competitions file, Gaps). The participant repo's methodology, timing several variants inside untimed `prepare()` and running a local judge replica on a rented GPU, is exactly what maxbox's adapter should automate (competitions B43–B44; [muse-spark-open-kernels](https://github.com/theluckystrike/muse-spark-open-kernels)).

The SGLang file's KQ2 gives the per-problem baseline paths, which define what "beat SGLang" means and which maxbox kernels an Ada-trained agent would be porting: `muse_bf16_proj` is `bf16_gemm_dispatch` with `Bf16GemmBackend {auto, cutedsl, gemv}` and FlashInfer split-K tactic tables, LM head "GEMM + split-K reduce (cuBLASLt)"; `muse_attention_decode` is `trtllm_mha` (FlashInfer XQA, FP8 E4M3 KV, page 128) with the fused Triton `muse_spark_qk_norm_rope_store` and CUDA norm+gate, Helion variants optional; `muse_moe_w4a16` has no in-tree GPU W4A16 path beyond Marlin (`moe_wna16_marlin`, `fused_marlin_moe`) because the INT4 WOQ experts are an Intel AMX path; `muse_decode_layer` composes a JIT split-K FP32 router GEMM on a side stream, fused Triton routing, FlashInfer TRT-LLM NVFP4 MoE with `do_finalize=False`, a CuTe-DSL/Helion weighted-sum finalize, layer-boundary fusion and breakable CUDA graphs; `muse_prefill_layer` is LayerNorm-SP plus DeepGEMM MegaMoE with `weight_layout="trtllm"` and a 256-entry FP32 shared-memory reciprocal table ([unquant.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/quantization/unquant.py); [muse_spark_megamoe.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/muse_spark/muse_spark_megamoe.py); [PR #44798](https://github.com/sgl-project/sglang/pull/44798)). ## Every engine exposes the same six seams under different names

Across the engine files the seams reduce to a short list that maps onto maxbox slot contracts one-to-one: an attention-backend registry keyed by (arch, model type, layer type); a MoE runner × all-to-all pair chosen by a backend string or oracle; a quantization-config registry with per-scheme GEMM override; a speculative-proposer registry; a KV connector/tiering interface; a CUDA-graph/compile mode selector; and, in the newest engines, a kernel-level registry that ranks implementations by capability. vLLM's are the most explicit: `vllm/v1/attention/backends/registry.py` with `AttentionBackend`/`AttentionImpl` pairs selected by per-arch priority lists and `--attention-backend`/`-ac.mla_prefill_backend` flags; `FusedMoEPrepareAndFinalize` × `FusedMoEExpertsModular` composed by `FusedMoEModularKernel` and selected by `--moe-backend`, `--all2all-backend` and the `fused_moe/oracle`; `QuantizationConfig` subclasses with `@register_quantization_config` and `linear_backend_per_quant`; `CustomOp` with per-platform forwards; `PassManager` + `VllmInductorPass` gated by `-O` levels; `CUDAGraphMode` {NONE, PIECEWISE, FULL, FULL_AND_PIECEWISE, FULL_DECODE_ONLY}; proposer classes incl. `custom_class_proposer.py`; `KVConnectorBase_V1` + `MultiConnector`; `KVCacheCoordinator` → `SingleTypeKVCacheManager` per group; `vllm.platform_plugins` entry points ([attention backends](https://docs.vllm.ai/en/latest/design/attention_backends/); [fused MoE modular kernel](https://docs.vllm.ai/en/latest/design/fused_moe_modular_kernel/); [plugin system](https://docs.vllm.ai/en/latest/design/plugin_system/)). ## Ingestion plan: fingerprint-keyed dedup, six classification axes, 24-plugin first batch

The catalog should hold two record types, because the notes mix them: a **technique** (mechanism or policy, implementation-independent) and an **implementation** (a specific engine's code path, flag, version and status). Each note row becomes an implementation record first; techniques are created by the dedup pass; research rows without an engine implementation become techniques with an empty implementation list and a `candidate` status. Competitions Table A rows are a third type, **validation targets**, and Table B rows are **tactics** attached to a technique family rather than techniques themselves.

The technique schema: `technique_id`; `canonical_name`; `aliases[]` (seeded from the duplicate table in section 1); `family` (one of ~150, e.g. `fp8-kv`, `prefix-cache`, `eagle`, `megamoe`); `primary_slot` and `secondary_slots[]` from the 23-slot vocabulary shared by all ten files (quant-recipe, placement, expert-cache, offload-scheduler, moe-cpu, moe-gpu, linear-gpu, attn-prefill, attn-decode, recurrent-mixer, fused-elementwise, kv-dtype, kv-select, kv-allocator, kv-tier, sampler, spec, scheduler, executor, loader, os-config, parallelism, engine) plus the ML-file extensions resident-set, expert-prune, token-compression, model-arch; `kind` ∈ {kernel, policy, format, transform, model-arch, tooling}; `lossless_class` ∈ {bit-exact, distribution-preserving, model-native-approximation, lossy-gated}; `preconditions` as structured gates {`sm_min`, `sm_excluded[]`, `cpu_isa[]`, `interconnect`, `model_features[]`, `training_required` ∈ {TF, calib, train-aux, FT, arch}}; `regime` ∈ {prefill, decode, both, startup, offline} × batch bucket; `ada_status` ∈ {runs, runs-untested, algorithm-only, no}; `verification_gate` ∈ {tolerance-vs-reference, output-equivalence, distributional, KLD+task, long-context-retrieval, state-drift}; `evidence_grade` 0–3 mapped from the files' legends ([T]/[R]/[D]/[V] → 3; [S]/[B] → 2; [M]/† → 1; [U]/n/r → 0); `claimed_gains[]` {value, hardware, workload, source_url}; `licence`; `benchmark_coverage[]` (which Table A targets exercise it); `box_relevance` (a bytes-removed or sync-removed score for the user's machine); `source_rows[]` as `{file, section, row}` pointers. The implementation schema: `engine`, `version_or_commit`, `entry_point` (class/flag/file), `status` ∈ {stable, experimental, deprecated, removed, unverified}, `date`, `source_url`, `note_row`.

The dedup key is a **mechanism fingerprint**, not a name: `(primary_slot, operation, numeric format or algorithm, granularity, phase)`. Under this key vLLM D#64, SGLang #106, TRT-LLM #28, TGI #31 and Sonar #99 all hash to `kv-dtype / store / fp8-e4m3 / per-tensor-or-per-token / both`, while vLLM D#66 (`fp8_ds_mla`, latent) and D#67 (NVFP4) stay separate. A second pass merges on normalized aliases (EAGLE/EAGLE-3/EAGLE-3.1; DFlash/DFlash-2/"block diffusion drafter"; MTP/NEXTN/"frozen-KV MTP"; DSpark/"dflash.py in DeepInfer"; MegaMoE/"Mega MoE"/`megamoe`; RadixAttention/"radix cache"/"automatic prefix caching"/"block reuse"). A third pass attaches research rows to engine techniques when the engine file names the paper or the paper names the engine (FlashInfer MLSys'25 ↔ vLLM A#4; Marlin PPoPP'25 ↔ vLLM E#79; QServe ↔ TRT #13; XGrammar ↔ vLLM M#235; Jenga ↔ vLLM C#62; KTransformers SOSP'25 ↔ llamacpp #183). A fourth pass folds the kvpress block (TRT #335–366) into ML section C as implementations of those papers. Expected yield: engine files 1,450 rows → ~450 techniques; research files 1,100 rows → ~550 techniques after attaching ~150 to engine entries; compilers 269 → ~60 techniques plus ~180 implementation/tooling records; competitions 141 → 75 validation targets and 66 tactics. Six classification axes then drive maxbox's planner: slot, kind (mechanism vs policy, which decides whether the verification gate is a kernel tolerance test or an output-equivalence test), lossless class, hardware gate, maturity, and box relevance.

For the user's box the first batch should follow the ranking the earlier report derived from the bandwidth ladder (VRAM 1,008 GB/s, DDR4 29.1 GB/s measured copy, PCIe 3.0 ~11.7 GB/s, USB/9p 0.24 GB/s) but expressed as catalog entries with reference implementations to test against. Tier 0 is configuration and policy search on the pinned llama.cpp v0.7.0, lossless and zero-risk: (1) placement search over `--fit`, `-ot`, `--n-cpu-moe` (llamacpp #114–118); (2) `--moe-cache-mib` A/B at several sizes with hit-rate logging and the `n_expert_used` silent-disable check (#119; 2.2× on a 5090 per the blog, 1.57–1.62× on a PCIe-4.0 4090 per the PR) ([developersdigest](https://www.developersdigest.tech/blog/llama-cpp-moe-offload-n-cpu-moe-vs-moe-cache-2026); [PR #29887](https://github.com/ggml-org/llama.cpp/pull/29887)); (3) `-b/-ub` sweep to find the real CPU-vs-stream crossover (#113); (4) `-ctk/-ctv q8_0` with Hadamard rotation gated by a 32K NIAH run (#84–87); (5) `--spec-synth-len/rates` verification-cost curve before any drafter, then `ngram-mod`, `draft-mtp`, `draft-dflash` with `--spec-draft-conf-min` (#96–108); (6) threads, `--poll`, `--numa`, graph-split count and `--load-mode` A/B (#61–62, #121); (7) `.wslconfig memory=` and moving GGUFs off 9p (earlier report, os-config). The validation side of the first batch is the KernelBot adapter (`task.yml` + `reference.py` + `generate_input/ref_kernel/check_implementation`, exit code 112, modes test/benchmark/leaderboard/profile) extended with OKC's graph-capture check and untimed `prepare()`, and a second adapter implementing the SOL-ExecBench/FastKernels protocol (subprocess, L2 flush, 10/50 timing, calibrated tolerances, hidden distributions, peak memory, reward-hack scans). OKC's five problems are H200 targets, but their shapes and tolerances, once fetched, are the best public oracle for the five slots maxbox cares about most (skinny BF16 GEMM, FP8-KV SWA/GQA decode attention, W4A16 grouped MoE, full decode layer, full prefill layer), and the adapter can run them on the 4090 for correctness and relative-speedup tracking against FlashInfer's FA2 and Marlin even though absolute H200 scores are out of reach. Everything in the Hopper/Blackwell/AMX columns of section 2 enters the catalog with `ada_status = no` and `box_relevance = 0`, kept for the day the machine or the user's objective changes; the results database should be keyed by the whole platform tuple (GPU, link generation, CPU ISA, RAM bandwidth, driver, model, quant, shape bucket), because the same 4090 on a PCIe 4.0 or AVX-512 host would reorder every tier above.

## Conclusion

The source-by-source pass changes the shape of the problem from "collect techniques" to "collect references". The three big production engines plus FlashInfer and DeepSeek's libraries have converged so tightly that nearly every technique maxbox would want on a datacenter GPU already has three independent implementations and a documented registry slot; the research venues contribute depth within four slots and almost nothing that the engines have not already absorbed within two quarters. That means the catalog's value is not breadth but provenance: for each of the ~60 multi-engine techniques, maxbox can name the incumbent kernel, the flag that enables it, the version it landed in and the benchmark that exercises it, which is exactly the information a verification harness needs and a generator does not. The sm_89 line, by contrast, is where the engines go quiet. Nobody upstream ships Ada FP8 blockwise GEMM, an Ada DSA indexer, an Ada fused GDN decode step or AVX2-without-VNNI expert GEMV tuned per GGUF type, and those are the places where a per-platform plugin is both legitimate specialization and unlikely to be beaten by a library.

Two consequences follow for the ingestion queue. First, fingerprint-based dedup should run before any gain numbers are trusted, because the same claim (MegaMoE's 1.06–1.32×, DFlash's 1.85× on MiMo, EAGLE-3's 3.02×) recurs across files with different hardware attached, and a catalog that stores gains per implementation record rather than per technique will not conflate a B300 number with an H100 one. Second, the validation adapters are the critical path, not the plugin list: OKC, GPU MODE, SOL-ExecBench, FastKernels and KernelBench-Verified have independently arrived at the same protocol and the same catalogue of exploits, so building one harness that speaks `task.yml` and one that speaks the subprocess/L2-flush/hidden-distribution protocol gives maxbox external validation for every slot on day one, on a 4090 today and on whatever hardware the user runs next.
