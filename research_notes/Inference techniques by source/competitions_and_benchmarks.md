## Key Question 1: What is the Muse Spark Open Kernel Challenge (OKC), exactly — problems, rules, model, writeups?

### Takeaway
OKC (Meta × Paradigm × Andromeda, run by Paradigm) is a two-track $100K challenge: five single-H200 kernel problems (Oct 22–Nov 4 2026) scored vs SGLang's own kernels in-run, then an 8×H200 SGLang-patch serving track (Nov 5–19 2026) where all prize money is paid. The judge is explicitly built on GPU MODE's reference-kernels/kernelbot (Researcher Reciprocity License); submissions must be Apache-2.0, CUDA-graph-capturable, single Python file. No leader writeups exist yet (boards still open); one participant repo promises Apache-2.0 kernels after Nov 4.

### Cited Findings
- Challenge: "$100,000 challenge to see who can make Muse Spark run fastest" — [Daniel Gross on X](https://x.com/danielgross/status/2113351902402613558); "Top prize is $50K + an H200 signed by Meta team", co-sponsored by Paradigm and Meta — [Matt Huang on X](https://x.com/matthuang/status/2113354212642066518)
- Model: Muse Spark Open, 816B total / 42B active, 1M context, natively multimodal, released Oct 15 2026 under the Muse Model License; runs on SGLang, vLLM, TensorRT-LLM, Transformers, MLX, llama.cpp, Unsloth — [Meta research blog](https://research.meta.ai/blog/muse-spark-open); HF: `meta-models/Muse-Spark-open-816B-A42B` — [PyTorch blog](https://pytorch.org/blog/muse-spark-open/)
- OKC model description: "open mixture-of-experts model with 256 experts and 4-bit weights"; top-8 of 256 experts at width 4096, SwiGLU, NVFP4 weights, per-expert output norm; gated GQA attention over paged FP8 KV cache with QK-norm, 2,048-token sliding window (RoPE) or full attention layers, gated normalized output; router in FP32 — [openkernelchallenge.dev/llms.txt](https://openkernelchallenge.dev/llms.txt)
- Helion kernels shipped in SGLang for Muse Spark Open: RoPE, RMSNorm, quantization etc., "1.03 – 3.95x speedups compared to custom kernels written in hardware specific languages (e.g. NVIDIA CUDA and CuTe DSL) on NVIDIA GB300"; portable to AMD MI350 with 3% end-to-end throughput gain; also "Helion megakernels" fusing multiple ops into one persistent kernel for low-latency inference — [PyTorch blog](https://pytorch.org/blog/muse-spark-open/)
- Five kernel problems (muse_bf16_proj, muse_attention_decode, muse_moe_w4a16, muse_decode_layer, muse_prefill_layer), rules, CLI, API, timeline, prizes, licensing: see Table A rows A1–A6 — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Prefill shapes: "753 new tokens on an 80K conversation, four conversations at once, and 16K first-turn chunks. Most time goes to one large grouped NVFP4 GEMM" — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Kernel rules: must be capturable in a CUDA graph (no `.item()`, `.cpu()`, `synchronize()`, no value-dependent allocation/control flow); `prepare(weights)` untimed up to 300 s (weights may be repacked/losslessly compressed but not change precision: NVFP4 stays NVFP4, BF16 stays BF16 or smaller; FP32 router may be BF16 hi+lo with FP32 accumulate); activations stay BF16 where SGLang keeps them BF16; FP8 KV cache stays FP8; queries may be rounded to FP8 E4M3 at coarsest; attention must cover every key (no top-k/sparse/block-skipping); native CUDA via `load_inline` — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Timing: "timed against SGLang's kernel in the same run"; compilation counts to run time-limit not score; final review reruns top entries on scored, held-out and nearby shapes, on medians; removal for timing tamper, work outside timed calls, output caching/replay, lower precision — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Serving track: patch SGLang at commit `a55ab7d5`, scored by throughput vs stock SGLang on 8×H200, runs ≤90 min; only `python/sglang` source/JSON files, no `model_loader/` changes, ≤720 KB, no line >400 chars, prebuilt `sgl-kernel` not rebuilt; must stay same model (8 routed experts/token, 2,048 window, all norms/param shapes); drafter DFlash with released weights (can be sped up, not changed/retrained/replaced); outputs must agree with stock as well as stock agrees with itself; every request returns exactly 220 tokens; TTFT ≤2× SGLang's at each load — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Limits: 10 scored + 20 check runs per problem per day; serving 1 scored + 3 checks/day; reset 00:00 UTC — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Prizes ($100K, serving board only): $50K + signed H200 / $30K / $10K / $3K / $2K / $1K×5 (6th–10th); top 50 on kernel leaderboard get serving priority — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Environment: image `lmsysorg/sglang:dev-muse-spark-open` with PyTorch, Triton, FlashInfer, DeepGEMM, TileLang, CuTe DSL, CUTLASS; no network — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Licensing: submissions Apache-2.0; "The judge builds on GPU MODE's reference-kernels and kernelbot, which are under the June 9 Researcher Reciprocity License. GPU MODE does not sponsor or endorse this challenge." — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- CLI `okc` (v0.7.1): `okc login/problems/show/init/submit/check/status/jobs/leaderboard/withdraw`, `okc serve init/diff/check/submit/status/jobs/leaderboard`, `okc api`, `okc whoami/update/logout/version`; install `curl -fsSL https://openkernelchallenge.dev/install.sh | sh`; HTTP API `https://openkernelchallenge.dev/api/v1` with Bearer `kc_...`; `GET /problems/{problem}` returns scored shapes and SGLang's time; a human must `okc login` to accept rules — [llms.txt](https://openkernelchallenge.dev/llms.txt)
- Independent audit (Mark Saroufim, GPU MODE): OKC's seeds fit reference-kernels' Cantor pairing mod 2^63−1; exit code 112 = KernelBot `VALIDATE_FAIL`; same modes `test/benchmark/leaderboard/profile`; `submission.py`, `generate_input/ref_kernel/check_implementation`, `problems/<p>/task.yml`+`reference.py` layout; `# okc: problem=...` directive ≈ `#!POPCORN leaderboard`; "OKC aggregates load speedups"; terms §13 require Apache-2.0; rules do not commit to releasing the submission dataset — [msaroufim/openkernelchallenge-audit](https://github.com/msaroufim/openkernelchallenge-audit)
- Participant repo (placeholder until Nov 4): muse_moe_w4a16 → "Custom CUDA W4A16 GEMM"; muse_decode_layer → "Fused glue plus custom MoE"; muse_bf16_proj → "Skinny GEMM path"; muse_attention_decode → "Fused sliding-window kernel, in progress"; method: bandwidth table vs 4.8 TB/s, batch variants timed in `prepare()`, local judge on rented GPU — [theluckystrike/muse-spark-open-kernels](https://github.com/theluckystrike/muse-spark-open-kernels)
- Community: HN thread exists — [HN 50107379](https://news.ycombinator.com/item?id=50107379); Interconnects coverage — [interconnects.ai](https://www.interconnects.ai/p/meta-shakes-up-the-frontiers-open)
- Related (not OKC): vLLM PR adds opt-in `--monokernel` decode path for Muse Spark Open on AMD MI355X fusing each decoder layer into one persistent kernel launch (60 of 62 layers) — [vllm PR #62766](https://github.com/vllm-project/vllm/pull/62766); TokenSpeed adds Muse Spark Open support — [tokenspeed PR #2388](https://github.com/lightseekorg/tokenspeed/pull/2388)

### Inferences
- The "62 layers" in the vLLM monokernel PR plus "256 experts, top-8, width 4096, TP8/EP8" from llms.txt are the only public architectural numbers; the full config is in the HF repo (not fetched).
- Because the judge is a KernelBot derivative, maxbox's existing GPU MODE adapter (task.yml + reference.py + `generate_input/ref_kernel/check_implementation`, exit code 112) should run OKC problems with little change. The key additions are: CUDA-graph capturability check, untimed `prepare()`, SGLang-in-run baseline, and per-load geomean aggregation.
- "Loads 1/16/32 users incl. 8-token verify" (user-provided) is consistent with llms.txt's "one decode step or an 8-token verify block" and "aggregates load speedups", but the exact load ladder is only exposed via `GET /problems/{problem}` / `GET /serving`.

### Gaps
- Exact tensor shapes, tolerances and the load ladder per problem: only retrievable via `okc show <problem>` / `GET /problems/{problem}` behind login; not public text.
- Cold-L2 rule and the current leaderboard speedups (1.45×/2.73×/2.33×/1.94×/1.74×, user-provided) could not be verified from any public page.
- No leader writeups exist yet (kernel boards close Nov 4 2026). Re-check `theluckystrike/muse-spark-open-kernels` and `openkernelchallenge.dev/leaderboard` after that date.
- Muse Spark Open's hidden size, layer count (62 implied), attention head counts, KV layout: not in blog posts fetched.

### Inferences
- The LLM-inference-relevant core across all suites converges on the same ~10 slots: FP8/MXFP4/NVFP4 GEMM, grouped/MoE GEMM, fused MoE (routing+experts+SwiGLU), MLA/GQA decode attention (paged, FP8 KV), sparse attention indexer, Gated DeltaNet/SSM scans, RMSNorm/RoPE/quant fusions, all-to-all/EP comms, and whole decoder layers (decode and prefill). maxbox's plugin taxonomy should use these as primary slots.
- Two "external-validation" families are directly runnable without a competition account: GPU MODE reference-kernels (KernelBot task.yml format; Researcher Reciprocity license) and SOL-ExecBench/FastKernels/KernelBench-Verified (public repos, published timing protocols with L2 flush + locked clocks). OKC's judge is a KernelBot derivative, so one adapter covers GPU MODE + OKC.
- Timing protocols are converging on: CUDA events, 10 warmup / 50 timed, L2 flush (256 MB zero) or cold-L2 per iteration, locked SM clocks (1.5 GHz on B200), subprocess isolation, hidden/perturbed input distributions, and explicit reward-hack detection (precision downgrade, monkey patching, stream injection, cached outputs).

- GPU MODE `problems/amd/*` and `problems/amd_202602/mxfp4-mm` READMEs returned 404 at the raw path I tried; shapes for fp8-mm, moe, mla-decode (MI300X) and mxfp4-mm/moe-mxfp4 (MI355X) must be read from `task.yml`/`reference.py` in the repo (clone it).

- MLPerf v6.0 per-benchmark TTFT/TPOT limits and accuracy targets live in the rules doc (not fetched); mlcommons.org page now reflects v6.1.

## Key Question 3: Techniques from winning/notable submissions — Table B

### Takeaway
Winning kernels on Blackwell and MI300/MI355 share a small set of moves: persistent + warp-specialized pipelines fed by TMA/multicast, hand-chosen L1/L2 cache-policy hints, PTX-level decode of FP4/FP8, host-side work sorting for grouped GEMM tails, fusing elementwise/norm/dequant into the matmul or attention loop, and (end-to-end) megakernels with speculative drafters. modded-nanoGPT's 92 records contribute a separable list of inference-transferable kernel/precision tricks (FA3, FP8 heads/MLPs, fused Triton kernels, CUDA-graph capture) versus training-only optimizer work.

## Key Question 4: Ready-to-use kernel datasets and libraries, with licenses

### Takeaway
Three large competition-derived datasets exist (kernelbot-data 532K rows, KernelBook 18K pairs, Sakana archive ~30K kernels); the first two are under GPU MODE's "June 9 Researcher Reciprocity License" (training on them requires reciprocity), the Sakana archive is CC-BY-4.0. Ready-kernel libraries (kernels-community, Liger-Kernel, Helion) are the practical plugin sources.

### Cited Findings
- **GPUMODE/kernelbot-data**: 532,026 rows, 10.2 GB; fields submission_id, leaderboard_id, problem_name, user_id, user_name, code_id, file_name, submission_time, status (6 classes), score, passed, mode, runner, code; covers AMD MI300 (fp8-gemm, moe, mla-decode, all2all, gemm+reducescatter, allgather+gemm), AMD $1.1M (mxfp4-mm 763, moe-mxfp4 764, mixed-mla 765, ~125k rows), trimul 496, Helion B200_Nebius 766–770, NVFP4 (gemv 595, gemm 597, dual_gemm 598, modal_dual_gemm 697, group_gemm 730), PMPP v2 (8), linalg (qr_v2, eigh, cholesky); latest row 2026-04-07; license "other" = June 9 Researcher Reciprocity License (adapts Open RAIL-D; "If you train on it, you let us generate"); B200_Nebius measurements "brittle"; Modal dual_gemm (697) more trustworthy — [HF](https://huggingface.co/datasets/GPUMODE/kernelbot-data)
- **GPUMODE/KernelBook**: 18,162 rows; fields entry_point, original_triton_code, python_code, triton_code, repo_name, module_name, synthetic, uuid, licenses, stars, sha, repo_link; PyTorch modules from The Stack v1 repos, Triton generated by `torch.compile` (PyTorch 2.5.0), reformatted like KernelBench; May 2025; Researcher Reciprocity License; underlying repos MIT/Apache/BSD/MPL etc. — [HF](https://huggingface.co/datasets/GPUMODE/KernelBook)
