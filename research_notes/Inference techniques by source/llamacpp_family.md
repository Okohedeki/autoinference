# Inference optimization techniques: llama.cpp / ggml family and larger-than-VRAM engines (as of 2026-10-23)

Scope: llama.cpp (pinned baseline v0.7.0, 2026-10-15; master at b11840 on 2026-10-23), ik_llama.cpp, ktransformers / KT-Kernel, ExLlamaV2/V3, PowerInfer / PowerInfer-2, mistral.rs, candle, MLC-LLM, Apple MLX / mlx-lm, "Strata" fork.
Method: repo trees (GitHub HTML + REST API), READMEs, docs/, release notes (newreleases.io mirror of v0.7.0), PR/discussion pages, plus web search for the Strata fork. 39 tool calls.
Verification legend used in the table: **[V]** = seen in a primary source this session (file exists in tree, flag in README, PR page, release note); **[S]** = secondary source only (blog / aggregator / search snippet); **[M]** = from prior knowledge, file/flag name confirmed but behaviour or gain not re-verified this session; **[U]** = unverified (could not find a primary source). Gains without a bracket are quoted from the linked source.

## Key question: Every inference optimization technique in these engines, one row per technique

### Takeaway
llama.cpp master (Oct 2026) exposes ~110 distinct optimization levers across CUDA kernel families (mmq per-arch configs, mmvq/mmvf/mmf, three FA kernel families, fused MoE routing/reduction, FWHT for KV rotation, Gated-DeltaNet/SSM/RWKV mixers), CPU paths (per-ISA vec_dot, repack, AMX, KleidiAI, llamafile tinyBLAS, tiled GEMM), seven memory/KV-cache classes (unified, iSWA, DSA, DSV4, MSA, hybrid, recurrent), 12 speculative types, and a server/placement surface (--fit, --n-cpu-moe, -ot, --moe-cache-mib, --cache-ram, --load-mode). ik_llama.cpp adds ~30 quant types and MLA/fused-MoE/SER/graph-split levers; ktransformers adds CPU MoE kernels (AMX/AVX512/AVX2), expert deferral and placement strategies; ExLlamaV3 adds QTIP-trellis EXL3 + 2-8 bit cache; mistral.rs/candle/MLC/MLX cover ISQ, PagedAttention, TVM-compiled kernels and unified-memory tricks. A Strata fork could not be located as a primary repo.

### Inferences

**Plugin seams for maxbox (where a per-technique plugin can attach):**
- **ggml backend registry / `GGML_BACKEND_DL`**: backends are loadable shared libraries selected at runtime with `--device`/`--list-devices`; multiple backends (e.g. CUDA + Vulkan) coexist in one build — [docs/build.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md). A plugin can ship a backend `.so/.dll` and the scheduler will consider its buffer types.
- **Buffer types + `-ot` regex**: `--override-tensor <regex>=<buffer type>` maps any tensor to any registered buffer type (CPU, CUDA0, host-pinned, HBM via hbm.cpp, RPC) — [server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). This is the universal placement seam shared by llama.cpp and ik_llama.cpp (ik PR 232).
- **`--fit` / `--fit-target` / `--n-cpu-moe` / `--moe-cache-mib`**: compose into a placement search space (VRAM margin × expert layers on CPU × expert cache size) that a per-machine optimizer can sweep with `llama-bench`.
- **Spec-type list**: `--spec-type` is comma-separated, so model-free n-gram variants can stack with draft types; `--spec-synth-*` gives a benchmarking hook that isolates verification overhead — [docs/speculative.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md).
- **Quant recipe seam**: `--tensor-type regex=type` + `--imatrix` (GGUF) in mainline; regex custom mixes (PR 244) in ik — both regex-driven, so one recipe DSL can target either.
- **ktransformers YAML injection**: `match`/`replace`/`kwargs(generate_device, prefill_device)` rules per module regex, plus SGLang `--kt-*` flags for expert placement strategy and deferral — [kt-kernel README](https://github.com/kvcache-ai/ktransformers/tree/main/kt-kernel).
- **mistral.rs topology YAML** and **MLC `tensor_parallel_shards`/quant mode strings** are the analogous seams in those engines.

**Subset that runs on the user's box (RTX 4090 sm_89 + i7-10700K AVX2-only + 64 GB DDR4, PCIe 3.0):**
- Runs: all llama.cpp CUDA rows (mmq uses Ampere config on Ada; int8 tensor cores present; fattn-mma-f16; CUDA graphs; FWHT; topk-moe; moe-cache), FA with quantized KV, Hadamard-rotated q4_0/q8_0 KV, all `--fit/--n-cpu-moe/-ot/--moe-cache-mib` placement levers, all 12 spec types, host prompt cache (`--cache-ram`, 64 GB RAM is the main asset), `--load-mode mmap|dio`, backend sampling. CPU side: AVX2 vec_dot paths, repack (Q4_0/Q4_K/IQ4_NL 8x8 blocks via AVX2), llamafile tinyBLAS AVX2, OpenBLAS — but **not** AMX, AVX512, VNNI (10700K is Comet Lake: AVX2+FMA only), KleidiAI, ZenDNN.
- ik_llama.cpp: all IQ*_K/KS/KT types have AVX2 CPU kernels (README lists Zen4, AVX2, NEON); `-rtr`, `-fmoe`, `-mla 2`, `-amb 512`, `-ser`, FlashMLA-3 CUDA (needs Ampere+, 4090 OK). AVX-VNNI rows do not apply.
- ktransformers: AVX2-only backend (2026-03-26) and LLAMAFILE backend run; AMX/AVX512 backends do not; CUDA wheel supports sm_89. Expert deferral and placement strategies apply.
- ExLlamaV3: EXL3 kernels (CUDA ≥12.4, "modern consumer NVIDIA") and AVX2 CPU expert offload run.
- PowerInfer: AVX2 + CUDA supported, but only ReLU-family models.
- mistral.rs / candle / MLC (CUDA or Vulkan) run; MLX does not (Apple only).
- Hardware-specific caveat: PCIe 3.0 x16 (~12 GB/s practical) makes expert-upload-bound techniques (`--moe-cache-mib` misses, ktransformers layerwise prefill) proportionally slower than the PCIe 5.0 RTX 5090 numbers quoted; 64 GB RAM caps CPU-resident expert weights at roughly a 100B-class MoE at ~4 bpw.
