# Quantization Formats/Methods and GEMM/GEMV Kernels for LLM Inference (catalog, through Oct 2026)

Scope note: Target is a plugin-based engine on a single RTX 4090 (Ada, sm_89: has INT8/INT4 and FP8 tensor-core MMA, no FP4 MMA, no TMA/wgmma), PCIe 3.0 x16, i7-10700K (AVX2 only, no AVX-512/AMX/AVX-VNNI), about 64 GB DDR4, running MoE models with experts partly on the CPU. Each entry uses this format: **Name (date)**: what it does | engine slot | hardware | gain and regime | quality | maturity | source. Slots used below: `weight-format` (on-disk/in-memory weight encoding), `quantizer` (offline PTQ/QAT algorithm that produces the format), `act-quant` (runtime activation quantization), `transform` (rotation/smoothing folded into weights), `linear-kernel-gpu` (dense GEMM/GEMV), `moe-kernel-gpu` (grouped expert GEMM), `linear-kernel-cpu`, `moe-kernel-cpu`.

## Q1. Weight-only formats and methods (what exists, slot, HW, gain, quality, maturity, sources)

### Takeaway
Weight-only quantization is the main lever for memory-bound batch-1 decode, which is the regime that matters for single-GPU plus CPU-offload MoE. The field splits into three families. (a) Scalar/group formats with fast kernels: GGUF k-quants, GPTQ/AWQ INT4, MXFP4/NVFP4, FP8, NF4, HQQ. (b) Non-uniform/LUT formats: SqueezeLLM, NF4, any4, IQ4_NL, FLUTE-served formats. (c) Vector/trellis/codebook formats that win at 2–3 bpw: QuIP#, AQLM, QTIP, EXL3, ik_llama.cpp IQ*_KT, GGUF i-quants. On Ada and AVX2 everything runs by dequantizing in-kernel, because no 4-bit float tensor-core math exists on either device. So the choice comes down to bits per weight against dequant cost, and the dequant cost hurts most on the AVX2 CPU.

### Cited Findings

**A. GGUF / llama.cpp family (`weight-format` + `quantizer`; all run on CUDA sm_89 and AVX2 CPU)**
- **Legacy quants Q4_0/Q4_1/Q5_0/Q5_1/Q8_0 (2023)**: 32-weight blocks with an FP16 scale (and min). Simplest and fastest to dequantize, but lower quality than k-quants at the same size. Production in llama.cpp. — [llama.cpp repo](https://github.com/ggml-org/llama.cpp)
- **k-quants Q2_K…Q6_K (Jun 2023, llama.cpp PR #1684)**: 256-weight super-blocks with 6/8-bit quantized sub-block scales. Mixes like Q4_K_M use more bits for sensitive tensors (attn_v, ffn_down). Q4_K_M is about 4.8 bpw (4.83 bpw measured for Qwen3.6-27B). This is the de facto standard for consumer inference. — [llama.cpp PR #1684](https://github.com/ggml-org/llama.cpp/pull/1684); bpw figure: [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]
- **i-quants IQ1_S, IQ1_M, IQ2_XXS/XS/S/M, IQ3_XXS/S/M, IQ4_XS, IQ4_NL (Jan–Mar 2024, ikawrakow)**: IQ2/IQ3 use E8-lattice-inspired codebooks (sign plus grid-index packing, in the spirit of QuIP#). IQ4_NL/IQ4_XS use a non-linear 16-value grid. Lower PPL than k-quants at 1.5–3.5 bpw. Dequant is LUT-heavy, which makes them slower than k-quants on CPU. Production. — [llama.cpp repo](https://github.com/ggml-org/llama.cpp); [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]
- **imatrix (importance matrix) (Jan 2024, llama.cpp PR #4861)**: collects per-channel activation statistics on calibration text and weights the rounding error during quantization (an AWQ/GPTQ-like importance signal without Hessian updates). Essentially required for good i-quants and for Q2–Q3 k-quants. Calibration-set choice matters (see Unsloth below). — [llama.cpp PR #4861](https://github.com/ggml-org/llama.cpp/pull/4861)
- **Ternary TQ1_0 / TQ2_0 (2024, llama.cpp)**: native ternary types for BitNet-b1.58-style models (about 1.69 and 2.06 bpw). — [llama.cpp repo](https://github.com/ggml-org/llama.cpp)
- **MXFP4 in GGUF (Aug 2025, introduced for gpt-oss)**: OCP microscaling FP4. 32-element blocks, one shared E8M0 exponent per block, E2M1 elements, 4.25 bpw. gpt-oss ships its MoE expert weights natively in MXFP4. llama.cpp supports it on CUDA/CPU/Metal/Vulkan. ik_llama.cpp implemented it for Zen4, AVX2, NEON, Metal and CUDA in PR #682. — Format: [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]; ik PR: [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]; model: [openai/gpt-oss](https://github.com/openai/gpt-oss)
- **NVFP4 in GGUF (Mar–Apr 2026)**: `GGML_TYPE_NVFP4 = 40`. CUDA dp4a kernel in PR #20644 (merged Mar 26, 2026). Generic MMQ in #21074 (Apr 1). Vulkan in #21455/#21539 (Apr 10/14). Native Blackwell sm_120 NVFP4 MMQ enabled in build b8967 (Apr 29, 2026). The format uses 16-element blocks, an E4M3 block scale and an FP32 per-tensor scale (about 4.5 bpw). On sm_89 or earlier there is no native path, only memory savings. On an RTX 5090, b8967 raised pp512 from 3,295 to 5,547 t/s while tg128 stayed flat at 73.6 t/s, which shows the native FP4 gain is a prefill effect. Quality versus Q4_K_M was not yet independently benchmarked. NVFP4 files were only about 7% smaller than Q4_K_M, and some uploads were larger. — [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]; [NVIDIA forum, llama.cpp native MXFP4 on Blackwell PR #17906](https://forums.developer.nvidia.com/t/llama-cpp-experimental-native-mxfp4-support-for-blackwell-pr/355639) [web-verified]
- **Unsloth Dynamic 2.0 GGUFs (Apr 2025 onward)**: per-layer, per-model choice of quant type across every quantizable tensor rather than a few, aiming to minimize mean KL divergence per extra byte. Uses a chat/instruct-oriented calibration set (Calibration_v3/v5) instead of Wikipedia-only imatrix data. The project reports lower KLD than baseline imatrix GGUFs on Gemma-3 27B. It is a `quantizer` recipe on top of standard GGUF types, so it needs no new kernels. The exact layer-scoring algorithm is not documented. — [Unsloth Dynamic 2.0 docs](https://unsloth.ai/docs/basics/unsloth-dynamic-2.0-ggufs) [web-verified]; [iThome coverage](https://www.ithome.com.tw/news/174118) [web-verified]

**B. ik_llama.cpp quant types (`weight-format`; CUDA plus AVX2 CPU; production in the ik fork only, not upstream)** [web-verified, all from the [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) unless noted]
- **IQ_K family IQ2_K, IQ3_K, IQ4_K, IQ5_K, IQ6_K (2024; PRs #6, #7, #14)**: non-linear grids with per-block scale tweaks. The author claims lower PPL than i-quants/k-quants at matching bpw. CUDA support arrived in PRs #417/#418. — [ik discussion #8](https://github.com/ikawrakow/ik_llama.cpp/discussions/8)
- **IQ_KS / IQ_KSS / IQ_KL family (IQ4_KS #83, IQ2_KS #85, IQ4_KSS #89, IQ5_KS #422, IQ2_KL #602)**: per-row scales instead of per-block, giving lower effective bpw at similar quality.
- **Trellis "KT" quants IQ1_KT, IQ2_KT, IQ3_KT, IQ4_KT (CUDA PR #113; CPU #441; IQ1_KT #616)**: QTIP-style trellis codes with an integer-based trellis chosen to keep CPU decode cost reasonable. They target extreme compression; faster CPU prompt processing came in PRs #482/#488. No bpw/PPL numbers were in the README.
- **Row-interleaved repacked types (_R4, _R8, _R16)**: weights repacked so the AVX2/Zen4/NEON kernels process 4/8/16 rows at once. The `-rtr` flag repacks CPU tensors at load. The README warns against `-rtr` with hybrid CPU/GPU MoE, because k-quants lack CUDA row-interleaved kernels and CPU-resident weights get copied to the GPU for large-batch prefill.
- **BitNet / ternary IQ1_BN, IQ2_BN (#44); Q1_0_G128_R8 (#2541); Prism ternary PQ2_0/PTQ1_0 (#2550)**.
- **CPU requirements**: AVX2 or better. AVX-VNNI optimizations exist (PRs #1446–#1482), but the i7-10700K lacks AVX-VNNI, so it gets the plain-AVX2 paths.

**C. GPU-centric PTQ methods producing INT4/INT3/INT2 group-quantized weights (`quantizer` → `weight-format`)**
- **GPTQ (Oct 2022, ICLR 2023)**: one-shot, layer-wise, Hessian-based (OBQ) error compensation. 3–4-bit group-wise with act-order. Served by Marlin/Machete/ExLlama/exllamav2/AutoGPTQ/GPTQModel. On Ada it works through the Marlin kernels in vLLM. — [arXiv 2210.17323](https://arxiv.org/abs/2210.17323); vLLM HW table: [vLLM quantization docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **GPTAQ / GPTQv2 (Apr 2025)**: asymmetric calibration that accounts for accumulated quantization error from earlier layers. Drop-in GPTQ improvement. — [arXiv 2504.02692](https://arxiv.org/abs/2504.02692)
- **AWQ (Jun 2023, MLSys 2024 best paper)**: activation-aware per-channel scaling that protects salient weights, no backprop. INT4 g128 with near-FP16 quality. Supported on Ada in vLLM, served by Marlin. The TinyChat kernel targets edge GPUs. — [arXiv 2306.00978](https://arxiv.org/abs/2306.00978); [mit-han-lab/llm-awq](https://github.com/mit-han-lab/llm-awq); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **SpQR (Jun 2023)**: 3–4-bit groups plus a sparse FP16 outlier matrix, near-lossless. Needs custom sparse+dense kernels, so it saw little production uptake. — [arXiv 2306.03078](https://arxiv.org/abs/2306.03078)
- **OmniQuant (Aug 2023, ICLR 2024)**: learnable weight clipping plus learnable equivalent transformation, block-wise. Supports W4A16, W3A16, W2A16, and also W4A4/W6A6. Outputs standard INT formats, so existing kernels apply. — [arXiv 2308.13137](https://arxiv.org/abs/2308.13137)
- **SqueezeLLM (Jun 2023, ICML 2024)**: sensitivity-weighted k-means non-uniform quantization (a per-channel LUT) plus dense-and-sparse outliers. Needs LUT kernels (FLUTE/LUT-GEMM style). — [arXiv 2306.07629](https://arxiv.org/abs/2306.07629)
- **Any-Precision LLM (Feb 2024, ICML 2024)**: one bit-plane model that can be served at 3–8 bits from a single memory footprint, using SqueezeLLM-style incremental upscaling and a custom bit-plane GEMV. Interesting as a runtime-switchable precision plugin; research-grade. — [arXiv 2402.10517](https://arxiv.org/abs/2402.10517)
- **HQQ, Half-Quadratic Quantization (Nov 2023, Mobius Labs)**: calibration-free, fast, optimizes zero-point/scale with a robust loss. 1–8 bit. Served through torch/gemlite Triton kernels and Marlin/BitBLAS backends. Useful for on-the-fly quantization inside an agent loop. — [HQQ blog](https://mobiusml.github.io/hqq_blog/); [mobiusml/hqq](https://github.com/mobiusml/hqq); [mobiusml/gemlite](https://github.com/mobiusml/gemlite)
- **LeanQuant (Jul 2024)**: loss-error-aware non-uniform grids for GPTQ-style quantization. — [arXiv 2407.10032](https://arxiv.org/abs/2407.10032)
- **MagR (Jun 2024)**: weight-magnitude-reduction preprocessing that improves subsequent GPTQ/RTN with no inference overhead. — [arXiv 2406.00800](https://arxiv.org/abs/2406.00800)
- **decoupleQ (Apr 2024, ByteDance)**: decouples the integer and scale parts of 2-bit quantization, with a W2A16 CUDA kernel. — [arXiv 2404.12759](https://arxiv.org/abs/2404.12759)
- **SliM-LLM (May 2024)**: salience-driven mixed-precision group bits (2/3-bit). — [arXiv 2405.14917](https://arxiv.org/abs/2405.14917)
- **ABQ-LLM (Aug 2024)**: arbitrary-bit (W2–W8, A4–A8) quantized inference built on binary-TC decomposition. — [arXiv 2408.08554](https://arxiv.org/abs/2408.08554) [web-verified]
- **HIGGS (Nov 2024, NAACL 2025)**: data-free Hadamard rotation plus MSE-optimal grids, motivated by a "linearity theorem" relating layer error to PPL. Also supports dynamic per-layer bit allocation. Integrated in HF transformers with FLUTE kernels. — [arXiv 2411.17525](https://arxiv.org/abs/2411.17525)
- **D²Quant (Feb 2026)**: weight-only sub-4-bit PTQ with a Dual-Scale Quantizer for down-projections plus a LayerNorm mean-shift correction. Qwen3-8B at 2-bit averages 57.22 over 7 zero-shot tasks versus 54.05 for the prior best. Paper only. — [arXiv 2602.02546](https://arxiv.org/abs/2602.02546) [web-verified]

**D. Vector / codebook / trellis quantization (`weight-format`; best quality at 2–3 bpw; decode cost is the issue)**
- **QuIP (Jul 2023, NeurIPS 2023)**: incoherence processing (random orthogonal rotations) plus LDLQ adaptive rounding. The first viable 2-bit PTQ. — [arXiv 2307.13304](https://arxiv.org/abs/2307.13304)
- **QuIP# (Feb 2024, ICML 2024)**: randomized Hadamard incoherence plus the E8 lattice codebook (E8P, 2 bpw) plus fine-tuning. Fast lookup-based decode kernels. Direct ancestor of the llama.cpp IQ2/IQ3 designs. — [arXiv 2402.04396](https://arxiv.org/abs/2402.04396); [Cornell-RelaxML/quip-sharp](https://github.com/Cornell-RelaxML/quip-sharp)
- **AQLM (Jan 2024, ICML 2024)**: additive multi-codebook quantization (MCQ) learned per layer. Pareto-optimal below 3 bpw at publication. Batch-1 GPU/CPU kernels exist; supported in vLLM and HF. Very slow to quantize. — [arXiv 2401.06118](https://arxiv.org/abs/2401.06118); [Vahe1994/AQLM](https://github.com/Vahe1994/AQLM)
- **PV-Tuning (May 2024, NeurIPS 2024)**: fine-tuning for extreme-compressed (AQLM/QuIP#) models that improves 1–2 bpw quality. — [arXiv 2405.14852](https://arxiv.org/abs/2405.14852)
- **GPTVQ (Feb 2024)**: GPTQ-style vector quantization with low-dimensional codebooks. — [arXiv 2402.15319](https://arxiv.org/abs/2402.15319)
- **VPTQ (Sep 2024, Microsoft)**: vector PTQ with second-order optimization at 2 bits. Has an inference kernel and models on HF. — [arXiv 2409.17066](https://arxiv.org/abs/2409.17066); [microsoft/VPTQ](https://github.com/microsoft/VPTQ)
- **QTIP (Jun 2024, NeurIPS 2024)**: trellis-coded quantization (a bitshift trellis with "computed" codebooks, so no large codebook in cache) plus incoherence processing. High-dimensional VQ quality at scalar-like decode cost. Improves on QuIP# at 2–4 bits. The basis for EXL3 and ik_llama.cpp KT quants. — [arXiv 2406.11235](https://arxiv.org/abs/2406.11235); [Cornell-RelaxML/qtip](https://github.com/Cornell-RelaxML/qtip)
- **EXL2 (late 2023, exllamav2)**: GPTQ-derived mixed per-layer bit allocation (2–8 bpw, any fractional average). CUDA-only, fast. Superseded by EXL3. — [turboderp/exllamav2](https://github.com/turboderp/exllamav2)
- **EXL3 (2025, exllamav3)**: a QTIP variant with a procedural codebook and tail-biting trellis, departing from QTIP in tensor regularization and packing. Uses Hadamard rotation. One independent RTX 5090 test measured EXL3 at 4.00 bpw with 0.0248 mean KLD at 5.79 GiB, against GGUF Q4_K_M at 0.0398 KLD and 6.62 GiB. Size-matched against Q5_K_M (7.84 GiB, KLD 0.0172), EXL3 4.0 bpw with embeddings came to 7.79 GiB. llama.cpp decoded 15–21% faster in size-matched pairs, while EXL3 prefilled up to 2.5x faster. The README says the GEMM kernel still needs work on Ampere and to stay memory-bound at low bitrates. GPU-only, so no CPU expert path. — [turboderp-org/exllamav3](https://github.com/turboderp-org/exllamav3) [web-verified]; [atomic.chat EXL3 vs GGUF](https://atomic.chat/blog/guides/exl3-vs-gguf) [web-verified]
- **NestQuant (Feb 2025)**: nested-lattice (Gosset) quantization of weights, activations and KV. Paper-stage. — [arXiv 2502.09720](https://arxiv.org/abs/2502.09720)
- **QMoE (Oct 2023)**: sub-1-bit (about 0.8 bpw) compression of trillion-parameter MoE (SwitchTransformer) with a custom dictionary decoder. MoE-specific, research. — [arXiv 2310.16795](https://arxiv.org/abs/2310.16795)

**E. Float / microscaling / normal-float formats (`weight-format`)**
- **OCP Microscaling MXFP8/MXFP6/MXFP4/MXINT8 (Sep 2023 spec)**: 32-element blocks with a shared E8M0 power-of-two scale. Hardware FP4/FP6 MMA exists only on Blackwell (sm_100/sm_120) and AMD MI350-class. On Ada they are storage formats that get dequantized in kernel. — [arXiv 2310.10537](https://arxiv.org/abs/2310.10537); [OCP MX spec v1.0](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf)
- **NVFP4 (2025, NVIDIA Blackwell)**: E2M1 with 16-element blocks, an E4M3 block scale and an FP32 tensor scale. More accurate than MXFP4 thanks to the smaller block and finer scale. — [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]
- **MR-GPTQ / Micro-Rotated GPTQ (Sep 2025, ICLR 2026)**: GPTQ with block-wise Hadamard rotations tailored to FP4. It argues NVFP4's small groups blunt outlier-mitigation methods and that MXFP4's power-of-two scales add large error. Best recovery is NVFP4 96.6% versus MXFP4 92.3%. Rotations matter much more for MXFP4, and for NVFP4 the best rotation size equals the group size. Reported speedups versus FP16: up to 3.6x layer-wise and 2.2x end-to-end on B200, and up to 6x layer-wise and 4x end-to-end on RTX 5090. These are Blackwell-only speedups. — [arXiv 2509.23202](https://arxiv.org/abs/2509.23202) [web-verified]
- **FP8 E4M3/E5M2 weights (2022 format paper)**: 8-bit float weights with per-tensor or per-channel scales. Ada sm_89 has native FP8 tensor cores, so FP8 runs as true W8A8 on the 4090 (see Q2). On Ampere, vLLM serves FP8 weights as W8A16 through FP8-Marlin. — [arXiv 2209.05433](https://arxiv.org/abs/2209.05433); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **FP6 / FP5 weight-only, FP6-LLM / TC-FPx (Jan 2024)**: kernel design for 6-bit and 5-bit float weights on tensor cores (A100-class and newer). A middle ground between INT4 quality loss and the cost of 8-bit. In DeepSpeed (shown as "DeepSpeedFP", supported on Ada in vLLM). — [arXiv 2401.14112](https://arxiv.org/abs/2401.14112); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **bitsandbytes NF4 / FP4 (May 2023, QLoRA)**: a 4-bit NormalFloat grid that is information-theoretically optimal for normally distributed weights, block size 64, with double quantization of scales. Simple, calibration-free, and slower than Marlin-class kernels for serving. Supported on Ada in vLLM. — [arXiv 2305.14314](https://arxiv.org/abs/2305.14314); [bitsandbytes](https://github.com/bitsandbytes-foundation/bitsandbytes); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **LLM.int8() (Aug 2022)**: INT8 vector-wise quantization plus FP16 decomposition of outlier features. Historic; slow mixed-precision path. — [arXiv 2208.07339](https://arxiv.org/abs/2208.07339)
- **any4 / any3 (Meta, ICML 2025)**: a learned per-row 16-value LUT (arbitrary 4-bit numeric format) with a tinygemm-based LUT GEMM. — [facebookresearch/any4](https://github.com/facebookresearch/any4)

**F. Ternary / binary / QAT (`weight-format` + training)**
- **BitNet (Oct 2023) and BitNet b1.58 (Feb 2024)**: ternary {-1,0,1} weights trained from scratch. b1.58 matches FP16 LLaMA in PPL and end-task performance from 3B up (per the paper). It needs native-ternary models; it cannot be applied post hoc to gpt-oss or Qwen. — [arXiv 2310.11453](https://arxiv.org/abs/2310.11453); [arXiv 2402.17764](https://arxiv.org/abs/2402.17764)
- **bitnet.cpp (Oct 2024)**: CPU inference for 1.58-bit models with I2_S/TL1/TL2 LUT kernels built on T-MAC. — [arXiv 2410.16144](https://arxiv.org/abs/2410.16144); [microsoft/BitNet](https://github.com/microsoft/BitNet)
- **BitNet a4.8 (Nov 2024) / BitNet v2 (Apr 2025)**: 4-bit activations for ternary models, with Hadamard in v2. — [arXiv 2411.04965](https://arxiv.org/abs/2411.04965); [arXiv 2504.18415](https://arxiv.org/abs/2504.18415)
- **Post-hoc binarization BiLLM (Feb 2024), PB-LLM (Oct 2023), OneBit (Feb 2024)**: 1-bit PTQ/QAT research with large quality loss. — [arXiv 2402.04291](https://arxiv.org/abs/2402.04291); [arXiv 2310.00034](https://arxiv.org/abs/2310.00034); [arXiv 2402.11295](https://arxiv.org/abs/2402.11295)
- **QAT methods LLM-QAT (May 2023), EfficientQAT (Jul 2024), ParetoQ (Feb 2025)**: ParetoQ maps the 1/1.58/2/3/4-bit QAT frontier and finds 2–3-bit QAT competitive. QAT models still use standard formats. (Note: Google's Gemma QAT releases and gpt-oss's MXFP4-native training show vendors increasingly ship QAT'd low-bit checkpoints.) — [arXiv 2305.17888](https://arxiv.org/abs/2305.17888); [arXiv 2407.11062](https://arxiv.org/abs/2407.11062); [arXiv 2502.02631](https://arxiv.org/abs/2502.02631)
- **MoE-specific mixed precision MoQE (Oct 2023)**: experts are more robust to low-bit quantization than dense FFNs, which justifies giving experts fewer bits than attention/shared layers. This is the pattern Unsloth/ik recipes use for MoE GGUFs. — [arXiv 2310.02410](https://arxiv.org/abs/2310.02410)

### Inferences
- For the target box, the useful weight-only plugins are: (1) GGUF k/i-quants plus imatrix, (2) ik IQ_K/IQ_KS plus KT trellis types, (3) MXFP4 (native for gpt-oss, so no requantization), (4) Unsloth-style per-tensor mixed-precision recipes, and (5) AWQ/GPTQ INT4 for GPU-resident layers served by Marlin. EXL3/QTIP give the best quality per byte but are GPU-only, so they suit only the GPU-resident subset of layers unless the engine adds a CPU trellis decoder (ik's KT types are exactly that).
- Native FP4 hardware gains (NVFP4/MXFP4 MMA) are a Blackwell prefill effect. The 5090 llama.cpp numbers show decode flat while pp512 rose 68%. On a 4090, FP4 formats are worth exactly their bpw (4.25–4.5), no more.
- Trellis/VQ formats move cost from memory to ALU. That is a good trade on the 4090 (about 1 TB/s and large INT throughput) but a riskier one on an AVX2 CPU without VNNI. A search agent should benchmark CPU-expert decode per format rather than assume the lowest bpw is fastest.

### Gaps
- No bpw/PPL table was retrieved for ik IQ*_KT types or IQ_KS against Unsloth UD quants on the target models (gpt-oss-120b, Qwen3.6-35B-A3B, Gemma 4 26B-A4B, GLM-5.3-Flash). The engine must measure these.
- The exllamav3 `doc/exl3.md` fetch returned 404, so EXL3 internals (K, L, codebook parameters) beyond the search summary are unverified.
- I found no evidence on whether gpt-oss MXFP4 experts lose quality when requantized to IQ4_XS/IQ4_KS for CPU speed.
- 2026 weight-only papers beyond D²Quant and MR-GPTQ were not exhaustively enumerated, because the search found no dedicated 2026 survey.

## Q2. Weight + activation quantization (W8A8, W4A8, W4A4, FP8 scaling, rotations)

### Takeaway
W+A quantization speeds up compute-bound prefill and large-batch decode by using INT8/INT4/FP8 tensor cores. At batch 1 it buys little beyond what weight-only already gives. On the 4090, FP8 W8A8 (native on sm_89), INT8 W8A8 (SmoothQuant-style) and INT4 W4A4 (Ada keeps INT4 MMA) are all hardware-feasible. Hopper-only kernels (DeepGEMM, Machete, wgmma-based FP8 grouped GEMM) are not. Rotation methods (QuaRot, SpinQuant, FlatQuant, DuQuant, MR-GPTQ) are offline `transform` plugins that make low-bit activations viable. Some fold fully into the weights; others need a runtime online Hadamard.

### Cited Findings
- **Ada tensor-core capabilities (2022 whitepaper)**: AD102 supports FP8 (E4M3/E5M2), INT8 and INT4 tensor-core math, has about 1 TB/s of memory bandwidth on the RTX 4090, and has no FP4. GeForce parts run FP8/FP16 MMA with FP32 accumulate at half the FP16-accumulate rate. — [NVIDIA Ada architecture whitepaper](https://images.nvidia.com/aem-dam/Solutions/geforce/ada/nvidia-ada-gpu-architecture.pdf)
- **vLLM hardware matrix**: FP8 W8A8 is supported on Ada, Hopper and AMD, but not Volta/Turing/Ampere. INT8 W8A8 is supported Turing through Hopper. INT8 W4A8 is listed for Arm CPU only. Marlin (GPTQ/AWQ/FP8/FP4) is supported on Ada; Turing lacks Marlin MXFP4. — [vLLM quantization docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **SmoothQuant (Nov 2022, ICML 2023)**: migrates activation outliers into weights through per-channel scaling, giving INT8 W8A8. The paper reports up to 1.56x speedup and 2x memory reduction. Production (TRT-LLM, vLLM via llm-compressor). Works on Ada INT8 tensor cores. — [arXiv 2211.10438](https://arxiv.org/abs/2211.10438)
- **ZeroQuant (Jun 2022)**: fine-grained group-wise weights plus per-token activations for INT8, with fused kernels. — [arXiv 2206.01861](https://arxiv.org/abs/2206.01861)
- **FP8 dynamic per-token / per-channel scaling (2023–2025)**: per-tensor static, per-token dynamic activation scales, or DeepSeek-V3-style 1x128 activation / 128x128 weight block scales. Ada sm_89 can run FP8 scaled-mm through CUTLASS/cuBLASLt. DeepSeek's block-scaled kernels (DeepGEMM) need sm_90/sm_100. — DeepGEMM requirements: [deepseek-ai/DeepGEMM](https://github.com/deepseek-ai/DeepGEMM) [web-verified]; vLLM FP8 on Ada: [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **QServe / QoQ (May 2024, MLSys 2025)**: W4A8KV4 with progressive group quantization, SmoothAttention and compute-aware weight reordering. Its kernels keep dequant in INT8 to avoid the CUDA-core overhead of W4A4 designs. The paper reports maximum serving throughput up 1.2x (A100) and 1.4x (L40S) on Llama-3-8B, and 2.4x (A100) and 3.5x (L40S) on Qwen1.5-72B, against TensorRT-LLM. L40S is Ada sm_89, so this is directly relevant. — [arXiv 2405.04532](https://arxiv.org/abs/2405.04532); [mit-han-lab/omniserve](https://github.com/mit-han-lab/omniserve)
- **QQQ (Jun 2024)**: W4A8 with adaptive smoothing plus Hessian compensation, with Marlin-derived W4A8 kernels. — [arXiv 2406.09904](https://arxiv.org/abs/2406.09904)
- **Atom (Oct 2023, MLSys 2024)**: W4A4 with mixed-precision outlier channels and reordering. The paper reports up to 7.73x throughput versus FP16 and 2.53x versus INT8 at serving batch sizes. Uses INT4 tensor cores (Ampere/Ada). — [arXiv 2310.19102](https://arxiv.org/abs/2310.19102)
- **QuaRot (Apr 2024, NeurIPS 2024)**: random Hadamard rotations of the hidden state remove outliers, enabling end-to-end 4-bit W/A/KV. LLaMA2-70B loses at most 0.47 WikiText-2 PPL. It needs online Hadamards (fast-hadamard-transform kernel) for the FFN-down input and attention. INT4 kernels target Ampere/Ada. — [arXiv 2404.00456](https://arxiv.org/abs/2404.00456); [spcl/QuaRot](https://github.com/spcl/QuaRot)
- **SpinQuant (May 2024, ICLR 2025)**: learned rotations (Cayley optimization) instead of random ones. W4A4KV4 narrows the zero-shot gap on LLaMA-2 7B to 2.9 points. Can be weight-folded-only (no online Hadamard) for weight-only use. — [arXiv 2405.16406](https://arxiv.org/abs/2405.16406); [facebookresearch/SpinQuant](https://github.com/facebookresearch/SpinQuant)
- **DuQuant (Jun 2024, NeurIPS 2024)**: rotation plus channel permutation (zigzag) to spread massive outliers. W4A4. — [arXiv 2406.01721](https://arxiv.org/abs/2406.01721)
- **FlatQuant (Oct 2024, ICML 2025)**: learnable affine (Kronecker-decomposed) transforms that flatten weights and activations. Reports W4A4 within about 1% of FP16 on LLaMA-3-70B, with fused kernels. — [arXiv 2410.09426](https://arxiv.org/abs/2410.09426); [ruikangliu/FlatQuant](https://github.com/ruikangliu/FlatQuant)
- **OSTQuant (Jan 2025, ICLR 2025)**: orthogonal plus scaling transforms optimized with a KL-Top loss for W4A4KV4. — [arXiv 2501.13987](https://arxiv.org/abs/2501.13987)
- **MR-GPTQ (Sep 2025, ICLR 2026)**: rotation-aware GPTQ for W4A4 MXFP4/NVFP4. Recovery is NVFP4 96.6% versus MXFP4 92.3%, and the speedups are Blackwell-only. — [arXiv 2509.23202](https://arxiv.org/abs/2509.23202) [web-verified]
- **Hadamard kernels**: Dao-AILab fast-hadamard-transform (CUDA, any arch) and PyTorch HadaCore (tensor-core Hadamard, 2024). ik_llama.cpp has Hadamard transforms for the K cache (CPU PR #1033, CUDA PR #1034) and V cache (PR #1527). — [Dao-AILab/fast-hadamard-transform](https://github.com/Dao-AILab/fast-hadamard-transform); [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]
- **llama.cpp's implicit W4A8**: MMQ/MMVQ quantize activations on the fly to q8_1 (or q8_K on CPU) and run int8 dot products (dp4a or int8 `mma.sync`). Every GGUF quant is therefore effectively WxA8 at runtime with integer math. — [llama.cpp ggml-cuda source](https://github.com/ggml-org/llama.cpp/tree/master/ggml/src/ggml-cuda)

### Inferences
- For batch-1 decode on the 4090, W+A quantization gains little, since the GEMV is bound by weight bandwidth. Its value is in prefill (long prompts, agent tool loops) and in the CPU-offload prefill path where batches go to the GPU. FP8 W8A8 for attention/dense layers and INT8-activation MMQ for quantized weights are the Ada-native choices.
- W4A4 INT (QuaRot/Atom-style) can run on Ada's INT4 tensor cores, but production engines have largely dropped INT4-activation paths in favor of FP8/FP4. A plugin would be an experiment, not a proven win.
- The rotations matter even for weight-only: SpinQuant/QuaRot/HIGGS/QTIP-style incoherence improves 2–4-bit weight quality and can be folded offline at zero runtime cost. That makes them a `transform` slot independent of activation precision.

### Gaps
- I found no measured W8A8 FP8 versus BF16 versus Marlin-INT4 prefill/decode comparison on an RTX 4090 for MoE models.
- I could not confirm whether vLLM/SGLang currently ship a working W4A4 INT4 path on sm_89 (October 2026).
- Newer 2026 rotation/W4A4 methods beyond MR-GPTQ were not enumerated.

## Q3. Kernels: GPU GEMM/GEMV, MoE grouped GEMM, CPU quantized GEMM

### Takeaway
On sm_89, the relevant GPU kernels are mma.sync-based (Ampere-style) designs: Marlin (plus Marlin-MoE and MXFP4/FP8 Marlin), llama.cpp MMQ/MMVQ, ExLlamaV2/V3 kernels, FLUTE, BitBLAS/Ladder, CUTLASS 2.x/3.x sm80/sm89 mixed-input GEMM, Triton GEMM and fused_moe, and tinygemm/gemlite. The Hopper/Blackwell-only set (Machete, DeepGEMM, FlashInfer TRT-LLM FP4 MoE, CUTLASS wgmma/TMA kernels, QuTLASS FP4) is out. On the AVX2 CPU, the choice is among ggml-cpu vec_dot plus repack, ik_llama.cpp's IQK kernels, llamafile tinyBLAS (sgemm), T-MAC LUT kernels, and KTransformers' kt-kernel LLAMAFILE (AVX2) backend.

### Cited Findings

**GPU dense GEMM/GEMV (`linear-kernel-gpu`)**
- **Marlin (Jan 2024; paper Aug 2024, PPoPP 2025)**: FP16xINT4 mixed-precision GEMM using async global loads, a carefully staged L2/smem pipeline and fast int4-to-fp16 dequant. Near-ideal (about 4x) speedup over FP16 up to batch sizes of about 16–32. Ampere+ (runs on Ada); production in vLLM/SGLang. vLLM's Marlin family now covers GPTQ, AWQ, FP8 (W8A16) and FP4 (including MXFP4) on Ada. — [arXiv 2408.11743](https://arxiv.org/abs/2408.11743); [IST-DASLab/marlin](https://github.com/IST-DASLab/marlin); [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **Sparse-Marlin (2024)**: Marlin plus 2:4 structured sparsity on sparse tensor cores (Ampere+). Needs 2:4-pruned weights, so it is not applicable to stock MoE checkpoints. — [IST-DASLab/Sparse-Marlin](https://github.com/IST-DASLab/Sparse-Marlin)
- **Machete (2024, Neural Magic/Red Hat, vLLM)**: CUTLASS-3 mixed-input GEMM built on wgmma/TMA, the successor to Marlin on Hopper. **Hopper-only (sm_90)**, so not usable on a 4090. vLLM falls back to Marlin on Ada. — [Neural Magic Machete blog](https://neuralmagic.com/blog/introducing-machete-a-mixed-input-gemm-kernel-optimized-for-nvidia-hopper-gpus/)

The CUTLASS Python DSL (CuTe DSL, 2025) enables JIT kernels. — [NVIDIA/cutlass](https://github.com/NVIDIA/cutlass)
- **cuBLASLt FP8 on Ada**: FP8 matmul with per-tensor scales is supported on sm_89 (used for vLLM FP8 W8A8 on Ada). — [vLLM docs](https://docs.vllm.ai/en/latest/features/quantization/index.html) [web-verified]
- **llama.cpp CUDA paths (production)**: (1) **MMVQ**, a quantized matrix-vector kernel using dp4a on q8_1-quantized activations, used for very small batches (decode). (2) **MMQ**, a quantized matmul using int8 `mma.sync` tensor-core tiles (Turing+) with stream-K style work decomposition, used for prefill and larger batches. (3) **dequant + cuBLAS**, which dequantizes to FP16 and calls cuBLAS GEMM; it is the fallback or the faster option for some large batches/types. (4) **MMF / FP16 paths** for unquantized weights. NVFP4 added dp4a (#20644) and MMQ (#21074) kernels in 2026. — [llama.cpp ggml-cuda](https://github.com/ggml-org/llama.cpp/tree/master/ggml/src/ggml-cuda); NVFP4 PRs: [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]
- **ik_llama.cpp CUDA**: CUDA kernels for IQ_K/IQ_KS/_R4 and KT types (PRs #417/#418/#461/#462/#113), better MoE on CUDA (PRs #248, #283), fused FFN ops (PR #229), and FlashMLA-3 on CUDA (Ampere+, PR #386). — [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]
- **ExLlamaV2 / ExLlamaV3 kernels**: EXL2 GEMV/GEMM with on-the-fly dequant (V2), and trellis-decode GEMM with Hadamard (V3). V3's GEMM is not yet memory-bound at low bitrates per its README. CUDA-only. — [turboderp-org/exllamav3](https://github.com/turboderp-org/exllamav3) [web-verified]
- **FLUTE (Jul 2024, EMNLP Findings 2024)**: a flexible LUT engine for non-uniform weight formats (NF4, AF4, learned LUTs, HIGGS) at 2/3/4 bits. Offline weight restructuring plus a vectorized shared-memory LUT. The paper claims 1.5–3x over existing GEMM kernels and 1.5–2x end-to-end throughput for LLaMA-3. Ampere/Ada (A6000/A100 tested). — [arXiv 2407.10960](https://arxiv.org/abs/2407.10960); [HanGuo97/flute](https://github.com/HanGuo97/flute)
- **LUT-GEMM (Jun 2022, ICLR 2024)**: BCQ (binary-coding quantization) LUT-based GEMV that removes dequantization. The paper reports a 2.1x improvement over OPTQ for OPT-175B at 3 bits on a single GPU. — [arXiv 2206.09557](https://arxiv.org/abs/2206.09557)
- **Ladder / BitBLAS (OSDI 2024, Microsoft)**: a tile-based compiler (on TVM) for arbitrary mixed-precision (INT1–8, FP4/FP8, NF4) GEMM/GEMV, with type-transform tiling. Supports Ampere/Ada. Used by HQQ, GPTQModel and vLLM experimentally. — [Ladder, OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/wang-lei); [microsoft/BitBLAS](https://github.com/microsoft/BitBLAS)

- **TC-FPx / FP6-LLM (Jan 2024)**: FP6/FP5 weight kernels on tensor cores (see Q1). — [arXiv 2401.14112](https://arxiv.org/abs/2401.14112)
- **tinygemm / torchao int4 weight-only, gemlite (2024)**: tinygemm is the int4 kernel in torchao (A16W4 with groupwise scales). gemlite is a set of Triton kernels for A16Wn (HQQ). — [pytorch/ao](https://github.com/pytorch/ao); [mobiusml/gemlite](https://github.com/mobiusml/gemlite)

### Inferences
- **sm_89 compatibility triage for the plugin catalog.** Usable: Marlin and Marlin-MoE (INT4/INT8/FP8/MXFP4/NVFP4 dequant), llama.cpp MMQ/MMVQ, ik CUDA, ExLlama V2/V3, FLUTE, BitBLAS/TileLang, Triton GEMM and fused_moe, CUTLASS 2.x (including FP8 sm89), cuBLASLt FP8, QServe W4A8 (L40S results), stream-K/split-K. Not usable: Machete, DeepGEMM, CUTLASS 3.x wgmma/TMA, FlashInfer/TRT-LLM native FP4 MoE, QuTLASS FP4, and anything needing tcgen05/TMEM.
- For batch-1 decode, the GEMV kernel's job is to stream weights at near-peak bandwidth (about 1 TB/s GPU, roughly 40–50 GB/s for dual-channel DDR4-3200 by arithmetic). Dequant must hide under memory time. MMVQ-style dp4a kernels and Marlin at batch 1 are the GPU baselines; a custom split-K GEMV per format is a natural agent target.
- For MoE prefill with few tokens per expert, grouped GEMM with a token-sorted layout (Triton fused_moe, MUL_MAT_ID) plus stream-K/split-K over the K dimension is what keeps the GPU busy. Per-GPU Triton block-size tuning (vLLM's config JSONs) is precisely the kind of search an agent can automate.

### Gaps
- I did not confirm which MXFP4 MoE backend vLLM picks on sm_89 for gpt-oss (Marlin versus Triton), nor llama.cpp's exact MXFP4 MMQ inner loop on Ada. Both should be checked in source.
- The Machete blog was not fetched this session; "Hopper-only" comes from prior knowledge plus vLLM's Ada→Marlin routing.
- No AVX2-specific benchmark comparing T-MAC, ik IQK, ggml-cpu and kt-kernel LLAMAFILE for MoE expert decode on a Comet Lake-class CPU was found.

## Q4. Which matter most for consumer single-GPU + CPU expert-offload MoE inference, and why

### Takeaway
Ranking for the target box: (1) per-tensor mixed-precision GGUF/ik formats chosen by device placement, meaning low-bpw but CPU-cheap types for CPU experts and higher-quality types for GPU attention/shared layers. (2) The CPU AVX2 expert GEMV kernels (ik IQK, ggml-cpu, kt-kernel LLAMAFILE, T-MAC), because CPU memory bandwidth is the decode bottleneck. (3) GPU MMQ/Marlin-class mixed-input kernels with grouped-expert support for the GPU-resident share and for PCIe-offloaded prefill. (4) Native MXFP4 handling for gpt-oss to avoid requantization loss. Everything that needs Hopper/Blackwell (DeepGEMM, Machete, native FP4 MMA) is irrelevant to this machine.

### Cited Findings
- Hybrid CPU/GPU MoE inference keeps hot or dense parts on the GPU and runs expert computation on the CPU (KTransformers, ik `--cpu-moe`/`--n-cpu-moe`, tensor overrides). — [KTransformers docs](https://docsearch.algolia.com/mcp/docs/repo/kvcache-ai/ktransformers) [web-verified]; [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]
- ik_llama.cpp warns that row-interleaved CPU repacking conflicts with hybrid CPU/GPU MoE, because CPU-resident weights get used by GPU kernels during large-batch prefill. So the CPU-optimal layout and the GPU-offload layout are in tension, and an engine must pick per tensor. — [ik_llama.cpp README](https://github.com/ikawrakow/ik_llama.cpp) [web-verified]
- On Ada, FP4 formats give memory savings only, with no native compute path. — [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]
- Native-FP4 gains appear in prefill (pp512 +68%) but not decode (tg128 flat) even on Blackwell. — [insiderllm FP4 guide](https://insiderllm.com/guides/fp4-inference-llamacpp-nvfp4-mxfp4/) [web-verified]
- EXL3 beats GGUF on quality per byte and prefill but trails on decode, and it is GPU-only. — [atomic.chat EXL3 vs GGUF](https://atomic.chat/blog/guides/exl3-vs-gguf) [web-verified]
- MoE experts tolerate lower bit widths than dense layers. — [MoQE, arXiv 2310.02410](https://arxiv.org/abs/2310.02410)
- KTransformers' AVX2 path exists but is much slower than its AMX/AVX-512 paths. — [Phoronix](https://www.phoronix.com/news/KTransformers-0.5.3) [web-verified]
- QServe's W4A8 shows serving gains on Ada-class L40S. Those are high-batch numbers, not batch-1. — [arXiv 2405.04532](https://arxiv.org/abs/2405.04532)

### Inferences
- **Decode math, as a first-order model.** Tokens per second are roughly bandwidth divided by the bytes of active weights touched per token. For an A3B/A4B MoE with most experts on the CPU, the CPU side dominates. Dual-channel DDR4-3200 tops out at about 51 GB/s theoretical, against about 1 TB/s on the GPU, roughly 20x apart. Every bpw removed from CPU-resident experts converts nearly linearly into decode speed, provided the AVX2 dequant keeps up. That favors simple-to-decode low-bpw types (Q2_K/Q3_K, IQ_KS, IQ4_XS, MXFP4) on the CPU, and makes trellis/VQ types (KT, IQ2_XXS) a measured trade-off rather than an automatic win, given no VNNI.
- **Prefill.** With PCIe 3.0 x16 (about 16 GB/s), llama.cpp-style "copy CPU experts to the GPU for big batches" is limited by the link. CPU-side prefill GEMM quality (tinyBLAS/IQK repacked kernels) and GPU MMQ for the resident layers both matter. W8A8 FP8 on the GPU helps prefill only for the GPU-resident portion.
- **gpt-oss-120b.** Keep the MXFP4 experts as-is: llama.cpp/ik have MXFP4 CPU (AVX2) and CUDA kernels. Requantizing risks quality loss without a bandwidth gain, since 4.25 bpw is already competitive. Attention and other non-expert weights could use Q8_0/FP8 or BF16 on the GPU.
- **Qwen3.6-35B-A3B / Gemma 4 26B-A4B / GLM-5.3-Flash.** Unsloth-style per-tensor mixes (Dynamic 2.0) or ik IQ_K/IQ_KS mixes, with the imatrix built from chat-style calibration data, are the most promising quality-per-byte plugins. KLD against the BF16 model should be the acceptance metric, as Unsloth argues.
- **Highest-value plugin slots for the agent's search space:** (a) per-tensor quant-type assignment (a placement-aware search over bpw), (b) the CPU expert GEMV kernel per type (AVX2), (c) the GPU MoE grouped-GEMM tile config (Triton/MMQ block sizes, split-K), (d) the batch-size threshold for offloading CPU-expert prefill to the GPU, and (e) offline rotation/incoherence transforms (QuaRot/SpinQuant/HIGGS-style) to improve low-bit quality at zero runtime cost.
- **Low priority on this hardware:** DeepGEMM, Machete, CUTLASS 3.x, FlashInfer FP4 MoE, NVFP4/MXFP4 native MMA, AMX/AVX-512 kernels (kt-kernel AMX/RAWINT4), Sparse-Marlin (needs 2:4 weights), BitNet/ternary (needs native-ternary models), and W4A4 serving methods (batch-1 gains are small).

### Gaps
- I found no published end-to-end decode/prefill numbers for the exact target models on an RTX 4090 with an AVX2 CPU across GGUF/ik/EXL3/KTransformers. The engine's benchmark harness will have to generate them.
- The quality impact of mixed CPU/GPU quant assignments on gpt-oss-120b, Qwen3.6, Gemma 4 and GLM-5.3-Flash (KLD/PPL) is unmeasured in public sources I found.
- I found no reliable source quantifying AVX2 dequant throughput per GGUF type, meaning which types stay memory-bound on a 10700K. This is a key unknown for the CPU-expert format choice.
